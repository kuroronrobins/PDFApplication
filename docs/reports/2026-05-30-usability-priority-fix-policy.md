# 2026-05-30 Usability Priority Fix Policy

## Scope

`docs/reports/2026-05-30-pc-load-usability-audit.md` で確認した5件を、ユーザビリティー優先で修正するための確定方針を定義する。

この文書は実装前の方針決定であり、実装変更は含まない。次の `/goal` 実行時は、この文書を作業方針として扱う。

## Decision

PC負荷軽減は重要だが、主要な作業導線を止めたり、プレビューを空表示にしたり、ユーザーに事前展開や待ち状態の推測を強いる形では採用しない。

今後の判断基準は次の通り。

- ユーザーが押した主要コマンドは、変換や生成が必要でも、その場で開始できることを優先する。
- 負荷対策は「遅延生成」「優先キュー」「可視範囲生成」「キャンセル可能ジョブ」で行い、「ボタンを無効にする」「内容を見せない」「長大な横スクロールだけにする」ことで解決しない。
- 直列Office変換は維持する。ただし、待機、処理中、優先指定、失敗をカードと下部バーで明示する。
- 実PDFのページ編集は準備完了後に限るが、ファイル単位の出力予約、出力名設定、書き出し開始は変換完了前でも可能にする。
- 大量ページでも、ユーザーが目的ページへ直接到達できる操作を用意する。スクロールだけを唯一の移動手段にしない。

## Fix Policy By Finding

### 1. 書き出しプレビューは、未展開PDFでも実ページを表示する

方針:

- 書き出しプレビューを開いた時点で、現在ページの実画像生成を最優先で要求する。
- ファイルカード展開済みかどうかに依存しない。
- まず現在ページ、次に前後ページ、最後に可視フィルムストリップ範囲を生成する。
- 生成中はファイル名だけの静的プレースホルダーではなく、対象ページ番号、生成中状態、キャンセル不能/可能の区別が分かるローディング表示にする。
- 既存サムネイルがある場合は即時表示し、実プレビュー画像ができたら差し替える。

実装方向:

- `renderPdfThumbnailsStreaming` を全ページ固定ではなく、要求ページ番号リストを受け取れるAPIに分離または拡張する。
- 書き出しプレビュー側から、現在ページの `sourcePath/cachePath` と `originalPageNumber` を使ってオンデマンド生成する。
- `previewZoom: 0` のまま固定しない。大プレビューに必要な画像は別ジョブまたは別パラメータで生成する。

完了条件:

- 実PDFを一度も展開していなくても、書き出しプレビューで現在ページの内容が表示される。
- 1366x768で、生成中表示が他UIを押しつぶさない。
- 生成失敗時は対象ファイル名、ページ番号、理由が見える。

### 2. 大PDFの展開画面は、スクロールだけに依存しない

方針:

- ページタイムラインの仮想化は維持する。
- ただし、1200ページ級で目的ページに到達する手段を追加する。
- 展開領域は一画面ワークベンチ要件を守りつつ、操作対象として不足しない高さを確保する。

実装方向:

- 展開ヘッダーにページジャンプ入力を追加する。例: `ページ 350 へ`。
- 現在表示範囲を `p1-p72 / 1200` のように示す。
- 分割済み位置、除外ページ、装飾ページへ移動できる小さな一覧またはセグメントを追加する。
- タイムライン高さは下部出力バーを維持したまま、1366x768で最低2行分を目標に調整する。

完了条件:

- 1200ページ fixture で任意ページ番号へ直接移動できる。
- 分割線を置いたページへ戻れる。
- 表示ページ数を増やしても、ファイルカード領域と下部出力バーが破綻しない。

### 3. 書き出しプレビューのフィルムストリップは仮想化し、移動導線を増やす

方針:

- フィルムストリップは全ページDOM描画しない。
- 大量ページでは横スクロールだけを主導線にしない。
- 現在ページ、前後ページ、表示範囲、分割境界を優先する。

実装方向:

- フィルムストリップも仮想化する。
- ページ番号入力、前後10ページ移動、先頭/末尾移動を追加する。
- 分割後の出力ファイル単位で移動できる小さな出力セレクタを追加する。
- 現在ページの実プレビュー生成とフィルムストリップ画像生成は別優先度にする。大表示を先に出す。

完了条件:

- 1200ページ preview で `.filmstrip-thumb` が全1200件マウントされない。
- 目的ページへの移動に長大な横スクロールが必須ではない。
- 現在ページの大プレビューがフィルムストリップ生成待ちにブロックされない。

### 4. Officeのみのバッチでも、変換前に書き出し開始できる

方針:

- Officeファイルは変換前でも出力対象として扱う。
- `activePageCount === 0` だけを理由に、Officeのみワークスペースの `出力名`、`書き出し` を無効化しない。
- プレビューは、未変換Officeがある場合に「PDF化してプレビュー」へ進める導線にする。

実装方向:

- `buildOutputPlan` またはAppBar側の有効条件を、ページ数だけでなく「出力対象のファイルがあるか」で判断する。
- 書き出し開始時は既存の `processAllPendingEngineFiles` を活かし、未変換Officeを先に処理してから export へ進む。
- Office変換が失敗した場合、そのファイルを明示してジョブを失敗させる。ほかのファイルを勝手に出力しない。
- 出力名設定は、変換前でもファイル単位の予定名を編集できるようにする。分割による複数出力名はページ確定後に更新する。

完了条件:

- Word/Excel/PowerPointだけを追加した状態で、`書き出し` が開始できる。
- ジョブ中にOffice変換が走り、成功後にPDF出力へ進む。
- 変換失敗時に、対象Officeファイル名と原因がUIに残る。

### 5. Office変換キューは直列のまま、状態を明確化する

方針:

- Office COM安定性のため、既定の1件ずつ変換は維持する。
- ただし、待機状態を隠さない。
- 「優先」操作は、押した直後にUI上の状態変化が分かるようにする。

実装方向:

- `queued` はカード上に `PDF化待ち` と表示する。
- キュー内の順番を可能なら `待ち 2番目` のように表示する。
- `priority` が立ったファイルは `次にPDF化` と表示する。
- 下部バーに `PDF化: 1/4処理中、2件待ち` のような全体状態を表示する。
- 投入直後の `backgroundProcessingPausedUntil` による待ちが必要なら、UI上は `まもなく開始` と表示する。

完了条件:

- queued/converting/priority/error がカード上で見分けられる。
- Officeを複数追加しても、現在処理中、次に処理されるファイル、待機件数が分かる。
- 変換の直列処理は維持され、同時COM変換は導入しない。

## Implementation Order

1. P0: Officeのみ書き出し開始を可能にする。
2. P0: 書き出しプレビューのオンデマンド実ページ表示を実装する。
3. P0: Officeキュー状態をカードと下部バーに明示する。
4. P1: 書き出しプレビューのフィルムストリップを仮想化し、ページジャンプを追加する。
5. P1: 展開タイムラインにページジャンプと表示範囲表示を追加し、1366x768の高さ配分を調整する。

P0だけで止める場合も、P1の未実装項目をレポートに残す。P1まで完了した場合は、1200ページ fixture のDOM数、スクロール幅、スクリーンショットを必ず更新する。

## Non-Goals

- Office COMの同時実行数は増やさない。
- LibreOffice fallback は追加しない。
- 一時PDFキャッシュを永続化しない。
- 旧Flet UIや `archive/` 実装を復活させない。
- 左サイドバーや常設大型右パネルは追加しない。

## Verification Policy

最低限、次を実施する。

- `npm run typecheck`
- `npm run build`。sandboxの `spawn EPERM` が出る場合は、承認を得て外側で再実行する。
- 1366x768ブラウザ確認。
- `?fixture=large-pages` で大PDF相当の展開画面とプレビューを確認。
- `?fixture=hundred-files` でファイルカード大量表示が破綻していないことを確認。
- Office-only書き出しは、可能ならTauri runtimeで実Office COMを通す。実Officeが使えない場合はUI状態とジョブ導線を `NOT RUN` 理由つきでレポートする。

UI変更を含むため、スクリーンショットは `docs/reports/screenshots/` に保存する。

## Required Report

実装時は `docs/reports/` に新しい実装レポートを追加する。最低限、次を含める。

- Scope
- Changed files
- User-visible behavior
- Verification commands
- Screenshot paths
- Known limitations
- Remaining risks
- Next recommended step
